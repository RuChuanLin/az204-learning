# Step 3: Configure Web App Settings

This step is about **fine-tuning your App Service** environment by setting up app-specific configuration, SSL certs, diagnostic logging, and virtual directories. These features help you:

- Manage **environment variables** (like database connection strings)
- Secure your web app with **HTTPS**
- Capture **logs** for troubleshooting
- Organize sub-apps or custom paths using **virtual directory mappings**

We’ll address each of these in detail below.

---

## 3.1 Create Application Settings (Bound to Deployment Slots)

**Application settings** in Azure App Service are basically **key-value** pairs exposed to your app as environment variables. You can mark certain settings as “slot settings,” meaning those values remain in their specific deployment slot (e.g., staging, production) and do not swap when you do a slot swap.

### Steps to Create or Edit an Application Setting

1. **Portal** (GUI approach)
   1. In the **Azure Portal**, go to your **Web App** → **Settings** → **Environment variables**.
   2. Click **Add** to add a key and value (e.g., `MY_CUSTOM_VAR = "HelloWorld"`).
   3. If you only want this variable in this slot, toggle **Deployment slot setting** to **On**.
   4. Click **Save**.

2. **Azure CLI**  
   ```bash
   az webapp config appsettings set \
     --resource-group MyJavaAppRG \
     --name MyAwesomeJavaWebApp \
     --settings "MY_CUSTOM_VAR=HelloWorld" \
     --slot-settings "MY_SLOT_VAR=ValuePerSlot"
   ```
   - `--settings` apply globally (will be swapped to other slots).
   - `--slot-settings` remain bound to the current slot.

### Why Slot Settings Matter
- **Production secrets** like live database passwords stay in production slot.
- **Staging** can have a different database or a test API key.

## 3.2 SSL/TLS Certificates

### Options for Installing Certificates

1. **Free App Service Managed Certificate**  
   - Easiest route, but only supports **basic** SSL for a root custom domain (no wildcard).  
   - Renewed automatically by Azure.

2. **Bring Your Own Certificate**  
   - Purchase or generate your own cert (could be wildcard or EV).  
   - **Upload** it to App Service via the TLS/SSL settings blade.  
   - Bind the custom domain and apply the cert to enforce HTTPS.

3. **Let’s Encrypt Automation**  
   - Community solutions exist to generate and auto-renew Let’s Encrypt certs via an Azure WebJob or GitHub Action.  

### High-Level Steps to Use a Managed Certificate

1. **Add a custom domain** to your Web App (e.g., `www.contoso.com`).  
2. In **Portal** → **TLS/SSL settings** → **Private Key Certificates (Preview)** → **Create App Service Managed Certificate**.  
3. Select the domain from the drop-down.  
4. Once created, go to **Bindings** → **Add TLS/SSL Binding** → select the domain and the new cert.

With this, you’ll have **HTTPS** enabled for your custom domain at no extra cost.

## 3.3 Enable Diagnostic Logging

Diagnostic logging is crucial for **debugging** issues and **monitoring** your app’s health.

### Types of Logs in App Service

1. **Application Logging (Filesystem or Blob Storage)**  
   - Captures logs generated by your app code (e.g., `System.out.println`, `System.Diagnostics.Trace`, `log.info(...)`, etc.).  
   - Can be stored temporarily on the local filesystem or in Azure Blob Storage for longer retention.

2. **Web Server Logging**  
   - Logs raw HTTP request data (IIS logs on Windows, or Access Logs on Linux).  

3. **Detailed Error Messages**  
   - Provides verbose info if the app fails to load a page, typically for Windows-based apps.

4. **Container Logs** (for Linux/Container-based apps)  
   - Captures Docker container output and error streams (stdout/stderr).

### Enabling Logging

1. **Portal**  
   1. In **Portal** → **Monitoring** → **App Service logs**.  
   2. Turn **Application Logging (Filesystem)** **On**.  
   3. (Optional) Set a **Retention Period** (in days).  
   4. (Optional) Enable **Web Server Logging** and specify **File System** or **Storage**.  

2. **View Logs** via  
   - **Log Stream** in the Portal (real-time).  
   - `az webapp log tail` from CLI.  
   - Kudu (Advanced Tools) → **LogFiles** folder.  

**Note**: Filesystem logs are typically ephemeral. For production, consider **Azure Blob Storage** or **Application Insights** for a more robust solution.

## 3.4 Create Virtual App to Directory Mappings

This feature is handy if you want multiple sub-apps or frameworks in a single App Service. For example:

- You have a main Java app at the root,  
- You have a second mini-app or static site that should appear at `/api` or `/admin`.

### Steps to Configure a Virtual Directory

1. In **Portal** → **Configuration** → **Path Mappings**.  
2. **Virtual applications and directories**: Add a new mapping like:
   - **Virtual Path**: `/api`  
   - **Physical Path**: `site\wwwroot\api_folder` (or wherever your secondary code is deployed)
   - Toggle “Application” if it’s a separate deployable unit.  
3. **Save**. Now, requests to `https://<app>.azurewebsites.net/api` get routed to that subfolder.

**Why Use This?**  
- You can segment large apps or run multiple frameworks in one web app.  
- Might be used for backward compatibility if your old app references certain folder paths.
