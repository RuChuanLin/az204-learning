## 🔗 Overview: How `kubectl`, `minikube`, and Kubernetes Work Together

### 🧩 Roles

| Tool           | Role                                                                         |
| -------------- | ---------------------------------------------------------------------------- |
| **Minikube**   | Starts and runs a local Kubernetes **cluster** (inside Docker, VM, etc.)     |
| **kubectl**    | The **command-line tool** that sends API requests to a Kubernetes cluster    |
| **Kubernetes** | The **actual orchestrator** (the system that manages your pods/services/etc) |

So:

> ✅ **Minikube is the cluster**
> ✅ **Kubernetes runs inside Minikube (as containers in Docker)**
> ✅ **kubectl is the client** that talks to that cluster

---

## 🛠️ How `kubectl` Talks to Minikube's Cluster

When you run:

```bash
minikube start
```

Minikube:

1. Boots up a **Kubernetes cluster** (usually inside a Docker container or VM)
2. Generates a **Kubeconfig file** containing the connection info (IP address, certificate, etc.)
3. Sets that cluster as your current context using:

   ```bash
   kubectl config use-context minikube
   ```

So even though you installed `kubectl` and `minikube` separately, **Minikube wires them together** by updating the kubeconfig.

That’s why `kubectl get nodes` just works after `minikube start`.

---

## 📁 Where is the Connection Info Stored?

`kubectl` reads from:

```bash
~/.kube/config
```

You can check what `kubectl` is pointing at with:

```bash
kubectl config get-contexts
kubectl config current-context
```

Output example:

```
CURRENT   NAME       CLUSTER    AUTHINFO     NAMESPACE
*         minikube   minikube   minikube     default
```
